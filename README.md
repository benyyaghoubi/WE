سؤال ۱: تفاوت merge و rebase

هر دو دستور برای ترکیب تغییرات دو شاخه استفاده می‌شوند، اما تاریخچهٔ کامیت‌ها را به شکل متفاوتی تغییر می‌دهند.

دستور git merge:

تغییرات یک شاخه را با شاخهٔ فعلی ترکیب می‌کند. اگر شاخه‌ها از هم جدا شده باشند، معمولاً یک Merge Commit ساخته می‌شود که هر دو تاریخچه را حفظ می‌کند.

مثال: می‌خواهیم شاخهٔ feature را وارد main کنیم.

git switch main
git merge feature

این روش برای کار گروهی مناسب است؛ چون تاریخچهٔ شاخه‌ها و نقطهٔ ادغام مشخص باقی می‌ماند.

دستور git rebase:

کامیت‌های شاخهٔ فعلی را روی نوک شاخهٔ دیگری دوباره اعمال می‌کند. در نتیجه، تاریخچه معمولاً خطی‌تر می‌شود و شناسهٔ کامیت‌های بازسازی‌شده تغییر می‌کند.

git switch feature
git rebase main

این روش زمانی مناسب است که بخواهیم پیش از ادغام، تاریخچهٔ شاخهٔ قابلیت را مرتب و خطی کنیم.

تفاوت اصلی: merge تاریخچهٔ شاخه‌ها را حفظ می‌کند و ممکن است Merge Commit بسازد؛ اما rebase کامیت‌ها را دوباره اعمال می‌کند و تاریخچه را بازنویسی می‌کند. بنابراین بهتر است از rebase روی کامیت‌هایی که قبلاً در اختیار دیگر اعضای تیم قرار گرفته‌اند، بدون هماهنگی استفاده نکنیم.

سؤال ۲: انتخاب بخشی از تغییرات (Hunk)

Hunk بخشی از تغییرات یک فایل در خروجی diff است که خطوط اضافه‌شده، حذف‌شده یا اطراف آن‌ها را نشان می‌دهد.

برای بررسی تغییرات فایل:

git diff

برای اضافه‌کردن تعاملی بخش‌هایی از تغییرات فایل به Staging:

git add -p README.md

Git هر بخش را نمایش می‌دهد و می‌توان با گزینه‌های تعاملی تصمیم گرفت کدام بخش وارد Staging شود. گزینهٔ y بخش فعلی را اضافه می‌کند، n از آن عبور می‌کند و s در صورت امکان بخش را به قسمت‌های کوچک‌تر تقسیم می‌کند.

سپس می‌توان تغییرات آماده‌شده را بررسی و کامیت کرد:

git diff --cached
git commit -m "Update selected README sections"

این روش باعث می‌شود هر کامیت تغییرات مرتبط و منسجمی داشته باشد؛ در نتیجه بررسی تاریخچه، پیدا کردن خطاها و بازگرداندن تغییرات ساده‌تر می‌شود.

سؤال ۳: پیدا کردن منشأ خطا با git bisect

دستور git bisect برای پیدا کردن کامیتی استفاده می‌شود که یک خطا را وارد پروژه کرده است. این دستور با جست‌وجوی دودویی، محدودهٔ کامیت‌های سالم و معیوب را مرحله‌به‌مرحله کوچک می‌کند.

ابتدا جست‌وجو را شروع می‌کنیم:

git bisect start
git bisect bad
git bisect good <good-commit>

در این مثال، HEAD کامیت معیوب فعلی است و <good-commit> باید با شناسهٔ یک کامیت واقعی که می‌دانیم سالم بوده جایگزین شود.

Git یک کامیت میانی را انتخاب می‌کند. برنامه را در آن نسخه آزمایش می‌کنیم و نتیجه را اعلام می‌کنیم:

git bisect good

اگر خطا وجود نداشته باشد، یا:

git bisect bad

اگر خطا وجود داشته باشد. این روند تا شناسایی کامیت مسئول خطا ادامه پیدا می‌کند.

در پایان:

git bisect reset

برای مثال، اگر برنامه در نسخهٔ هفتهٔ قبل درست کار می‌کرده اما امروز دچار خطا شده است، bisect کمک می‌کند کامیتی را که خطا را وارد کرده پیدا کنیم.

مزیت: به‌جای بررسی تک‌تک کامیت‌ها، جست‌وجوی دودویی تعداد بررسی‌های موردنیاز را به‌طور قابل‌توجهی کاهش می‌دهد.

سؤال ۴: بررسی تغییرات پیش از کامیت
بخش اول: بررسی وضعیت مخزن

برای مشاهدهٔ وضعیت فایل‌ها و تشخیص تغییرات Staging‌شده و Staging‌نشده، از دستور زیر استفاده می‌کنیم:

git status

برای مشاهدهٔ تغییراتی که هنوز وارد Staging نشده‌اند:

git diff

برای مشاهدهٔ تغییراتی که وارد Staging شده‌اند و آمادهٔ کامیت هستند:

git diff --cached

تفاوت این دو دستور آن است که git diff تغییرات بین Working Tree و Staging Area را نمایش می‌دهد، اما git diff --cached تغییرات بین Staging Area و آخرین کامیت را نشان می‌دهد.

بخش دوم: اجرای کامیت معمولی

در صورت اجرای دستور زیر:

git commit -m "Update README"

فقط تغییراتی کامیت می‌شوند که قبلاً وارد Staging Area شده‌اند.

در سناریوی سؤال، تغییرات اولیهٔ README.md وارد Staging شده‌اند؛ اما فایل پس از آن دوباره ویرایش شده است. بنابراین:

تغییرات قبلی که وارد Staging شده‌اند، در کامیت قرار می‌گیرند.

ویرایش‌های جدید که هنوز وارد Staging نشده‌اند، در Working Tree باقی می‌مانند.

فایل‌های Untracked داخل پوشهٔ tmp/ نیز به‌صورت خودکار وارد کامیت نمی‌شوند.

بخش سوم: جلوگیری از اضافه‌شدن فایل‌های موقت

در ریشهٔ مخزن، فایلی به نام .gitignore ایجاد یا ویرایش می‌کنیم و این خط را در آن قرار می‌دهیم:

tmp/

این تنظیم باعث می‌شود فایل‌های پوشهٔ tmp/ که هنوز Untracked هستند، به‌طور معمول توسط Git نادیده گرفته شوند.

اما .gitignore برای فایل‌هایی که قبلاً Tracked شده‌اند کافی نیست؛ زیرا Git همچنان تغییرات آن فایل‌ها را پیگیری می‌کند. اگر لازم باشد پوشه‌ای که قبلاً Track شده از پیگیری خارج شود، می‌توان از دستور زیر استفاده کرد:

git rm -r --cached tmp/

این دستور فایل‌ها را از Index گیت خارج می‌کند، اما آن‌ها را از Working Tree حذف نمی‌کند.

سؤال ۵: رفع Merge Conflict در کار گروهی
بخش اول: علت رخ‌دادن Conflict

وقتی دو نفر یک خط مشترک را در یک فایل تغییر می‌دهند و Git نتواند به‌صورت خودکار تصمیم بگیرد کدام تغییر باید حفظ شود، هنگام ادغام ممکن است Merge Conflict رخ دهد.

البته هر تغییری که دو نفر در یک فایل ایجاد کنند الزاماً Conflict ایجاد نمی‌کند؛ اگر تغییرات در بخش‌های مستقل باشند، Git اغلب می‌تواند آن‌ها را خودکار ترکیب کند.

بخش دوم: شناسایی فایل و نسخه‌های متعارض

برای مشاهدهٔ وضعیت مخزن:

git status

Git فایل‌های دارای Conflict را مشخص می‌کند. با بازکردن فایل README.md، بخش متعارض ممکن است به این شکل دیده شود:

<<<<<<< HEAD
متن موجود در شاخه main
=======
متن موجود در شاخه feature-description
>>>>>>> feature-description

<<<<<<< HEAD شروع نسخهٔ شاخهٔ فعلی را نشان می‌دهد.

======= دو نسخه را از هم جدا می‌کند.

>>>>>>> feature-description پایان نسخهٔ شاخهٔ دیگر را مشخص می‌کند.

بخش چهارم: لغو Merge در حال انجام

اگر تصمیم بگیریم Merge را ادامه ندهیم، می‌توانیم دستور زیر را اجرا کنیم:

git merge --abort

این دستور تلاش می‌کند عملیات Merge در حال انجام را لغو کرده و وضعیت مخزن را به قبل از شروع آن برگرداند. با توجه به اینکه در صورت سؤال Working Tree پیش از Merge تمیز بوده است، این روش انتخاب مناسبی است.

سؤال ۶: انتخاب روش مناسب برای بازگرداندن تغییرات
بخش اول: حذف تغییرات Staging‌نشده از notes.txt

در این حالت، تغییرات فایل وارد Staging نشده‌اند و می‌خواهیم فقط همین فایل به آخرین نسخهٔ ثبت‌شده برگردد.

دستور مناسب:

git restore notes.txt

نتیجه: تغییرات ثبت‌نشدهٔ فایل notes.txt از Working Tree حذف می‌شوند و فایل به نسخهٔ آخرین کامیت برمی‌گردد. سایر فایل‌ها تغییر نمی‌کنند.

بخش دوم: خارج‌کردن notes.txt از Staging

در این حالت، تغییرات فایل وارد Staging شده‌اند، اما هنوز کامیت نشده‌اند و می‌خواهیم آن‌ها را از Staging خارج کنیم، بدون اینکه ویرایش‌ها از بین بروند.

دستور مناسب:

git restore --staged notes.txt

نتیجه: تغییرات فایل از Staging Area خارج می‌شوند، اما در Working Tree باقی می‌مانند. بنابراین می‌توان آن‌ها را دوباره بررسی یا اصلاح کرد.

بخش سوم: بازگرداندن اثر یک کامیت اشتباه روی شاخهٔ مشترک

در این سناریو، کامیت اشتباه روی main پوش شده و اعضای تیم آن را دریافت کرده‌اند. همچنین هدف، بازگرداندن اثر کامیت بدون حذف یا بازنویسی تاریخچه است.

روش مناسب استفاده از git revert است:

git revert <commit-id>

به‌جای <commit-id>، شناسهٔ کامیت اشتباه را قرار می‌دهیم.

نتیجه: Git یک کامیت جدید ایجاد می‌کند که تغییرات کامیت اشتباه را معکوس می‌کند. کامیت قبلی در تاریخچه باقی می‌ماند و تاریخچهٔ مشترک بازنویسی نمی‌شود.

استفاده از git reset برای حذف کامیت از تاریخچه و سپس Force Push در این موقعیت انتخاب مناسبی نیست؛ زیرا سایر اعضای تیم قبلاً آن تاریخچه را دریافت کرده‌اند و بازنویسی آن می‌تواند باعث ناسازگاری تاریخچهٔ محلی آن‌ها با مخزن مشترک شود.
